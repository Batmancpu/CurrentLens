## P0 — Preserve the installed app and its data

The main workflow still uses the runner's debug signing identity. [Signing draft #39](https://github.com/Batmancpu/CurrentLens/pull/39) records distinct certificate fingerprints from two actual APKs of the same package, both at versionCode 2.

| Build | SHA-256 of signing certificate |
| --- | --- |
| Main #112 | `dba85a1c1ac6b3a7b829850353724e7a847e2fa456a13ab3f983d66c245f30dd` |
| Main #116 | `28c1fc47020366d8ad1fd689935039b7b3c8b79675e93112a68e2e47452adb64` |
| Stability #320 | `bde1edc88fc1c9bc0b3a060293dc0889262a22378a41ea5fe252532a49004d14` |

1. Identify the installed package, versionCode and signer by the exact original APK or by inspecting the installed base APK. If inspecting from a computer with Android platform tools, use `adb shell pm path <package>` to locate the base APK, pull it with `adb pull`, and use `apksigner verify --print-certs <apk>` locally. Record only the package, version and public certificate fingerprint. The published APK contains the certificate, not the key that created the signature.
2. Match the signer before creating or provisioning a release key. If the install is Stability and the cached key still matches it, #414 has an existing candidate to verify; the cache regenerates a different key on a miss. If the install is main and a matching private keystore still exists on the machine or build service that signed it, use it through the owner's secret store. Android requires a matching application ID, signing certificate or valid signing lineage, and a versionCode accepted as an update. Use a strictly higher versionCode for the next published build. [Android update requirements](https://developer.android.com/google/play/app-updates).
3. If the matching signer is unavailable, keep the existing install and decide on local-data preservation first. The manifest has `android:allowBackup=false`. There is no demonstrated app export/import path in this audit. A new key cannot retrospectively update an old signature. Do not uninstall to test signing. For any one-time migration, verify preservation or get the owner's explicit choice before moving the installed app to a new signing identity.
4. Reconcile #39 with current integration once the signer and data route are known. The draft is open, diverged 42 integration commits / 6 signing commits from common parent `cc5a01b4e95b8f1250e5d0dda7535e8a485c7d84` at audit. A local merge simulation found conflicts in the branch ledger, known issues, handoff and session ledger. Preserve newer histories when reconciling. The draft's [key setup and workflow](https://github.com/Batmancpu/CurrentLens/blob/fix/stable-release-signing-2026-11-08/docs/RELEASE_SIGNING.md) use private repository Actions secrets and the public certificate fingerprint variable `CURRENTLENS_RELEASE_CERT_SHA256`. [Run #320](https://github.com/Batmancpu/CurrentLens/actions/runs/42457214182) validated the Stability path. The main secret-backed path and any handset update are still unverified.
5. Verify the next signed candidate's app ID, certificate and versionCode before installation. Test update-in-place and confirm Saved, reading and quiz history still open. Preserve an encrypted backup of the matching long-lived key outside the repository. Keep release publication downstream of the migration decision and verification.
